01

The system in one picture

Level 1 · System context

Producers submit facts. Kansoku validates and buffers those facts durably, writes them efficiently, and exposes named analytical questions. Applications retain ownership of their business workflows and user records.

Write boundary

202 means queued

HTTP acceptance follows durable enqueue. Query visibility follows a later ClickHouse flush; acceptance provides no read-after-write guarantee.

Read boundary

Metrics have semantics

Queries choose raw facts, current identity resolution, or precomputed aggregate states. Exact and approximate results answer different questions.

Ownership boundary

Facts stay analytical

Kansoku owns analytics contracts, credentials, identity evidence, and metrics. It does not run application business workflows or own account records.

02

One service, coordinated lifetimes

Level 2 · Runtime components

Warp, the writer, queue-depth poller, and rejection cleanup share one supervised process. Unexpected subsystem termination ends the HTTP lifetime. A separate kansoku-admin executable coordinates maintenance through persisted PostgreSQL fences.

Startup sequence
  1. Load configurationParse environment settings and install SIGTERM / SIGINT handlers.
  2. Acquire durable connectionsCreate the PostgreSQL pool; provision the named PGMQ queue after migrations have installed its schema.
  3. Prepare reads and telemetryCreate the ClickHouse query pool, maintenance-lock pool, trace provider, pipeline instruments, heartbeat, and queue sample state.
  4. Start coordinated workRun the writer, poller, and quarantine cleanup; coordinate their lifetimes with the HTTP server.
Concurrency & resource ownership

Keep inserts off query sockets

The writer owns a dedicated, cached ClickHouse native-protocol connection. A failed insert discards that handle; the next delivery opens a fresh one.

Metric handlers borrow from a separate fixed-size pool, defaulting to four query connections. PostgreSQL pooling is shared by credential checks, queue producers, queue processing, and saved cohort/metric-definition management.

Effects stay explicit

The base runtime uses Log, Reader Config, and IOE. Ingestion and writer runners add queue, error, concurrency, and tracing interpreters where needed.

The writer's acknowledgement boundary

A Shibuya batch processor groups messages under one batch key, without aggregate ordering. Decoding happens per message, followed by one ClickHouse insert for all valid events. This is a throughput-oriented ingestion pipeline.

Insert attempts have a 30-second deadline. Bounded buffers limit retained deliveries to 2 × writerBatch + adapterBatch + 3 (11,003 at defaults). The configured delivery maximum is effectively non-exhausting; durable capacity and eventual recovery remain required. Graceful shutdown has a 30-second drain and 35-second total deadline.

03

Follow an event across the durable boundary

Level 2 → 3 · HTTP contract & processing sequence

Three ingest routes share validation, normalization, enrichment, credential rate limits, and immutable event acceptance. Authentication supplies the account; PostgreSQL commits the acceptance record and queue send in one transaction.

Authentication

Account identity is authoritative

The single/batch routes accept ksk_w_… write keys and ksk_s_… service tokens through Bearer authorization or X-Api-Key. Only service tokens permit metric reads. Beacon uses a body write key.

Authorization takes precedence if both headers exist, even if malformed. Each request checks a SHA-256 token hash in PostgreSQL; revocation takes effect on the next request.

HTTP admission

Reject at the right level

Defaults are 5 MiB per body and 500 events per batch. Invalid JSON or an array that cannot decode returns 400. Body or batch overflow returns 413.

A decoded, in-limit batch partitions events independently: new valid entries queue, equal retries acknowledge, and invalid or conflicting entries return zero-based rejection indices. Successful batch processing returns 202 even if every event is rejected.

One immutable logical event

(accountId, eventId) identifies a fact permanently. The acceptance ledger hashes canonical producer JSON, excluding server-owned account and receipt fields and delivery-only sentAt. An equal retry preserves the first normalization, enrichment, and trait eligibility; changed content is rejected with event_id_conflict. Accepted hashes and erasure dispositions outlive payload retention.

Browser exit transport

Body-authenticated beacon

POST /v1/beacon accepts {writeKey, batch} as UTF-8 JSON using text/plain or application/json. Only public write keys are allowed; service tokens and header credentials are rejected. Origin policy runs before ingest side effects.

The same byte/count limits, per-key bucket, partial acceptance, and counters apply. A true return from sendBeacon confirms browser queue admission only. Keep event IDs for an acknowledged retry and budget the complete outstanding UTF-8 envelopes conservatively below 60 KiB.

Admission & diagnostics

Bound work before persistence

Per-credential, per-process token buckets default to 2,000 submitted events/s and a 10,000-event burst, shared across transports. Throttling returns 429 with Retry-After.

Opt-in quarantine captures original individual objects for declared-schema failures with a 250 ms best-effort write budget. Defaults are 14-day expiry, 10,000 rows per account, and a 16 KiB payload cap; startup/hourly cleanup enforces eventual bounds.

Enrichment is fixed at first acceptance

Bounded request user-agent parsing derives browser, OS, device class, and bot categories. A Boolean context.bot=true can add a bot flag; false cannot clear a server match. Versioned channel rules prioritize email, paid social/search, other campaigns, organic search/social, referral, and direct/other traffic. Accepted enrichment survives queue retries and replay unchanged.

Optional country lookup requires an MMDB and explicit trusted-proxy CIDRs. Forwarded addresses are considered only from a trusted socket peer, using a validated chain; only the resulting country code is stored. Raw request addresses are not copied into events, queues, logs, or spans. Classification remains an approximation; rule updates do not silently rewrite accepted history.

Schema governance is executable

The registry in kansoku-api drives validation and the deterministic schema catalog. An omitted schemaVersion means version 1. Producer SDK boundary and delivery behavior

The Haskell client derives routes and types from kansoku-api. Defaults: batches of 100, a five-second flush interval, a 10,000-event memory buffer, five retries, and 100 ms exponential-backoff base. Buffer-full drops, permanent delivery failures, and server-side rejections increase droppedCount.

The SDK buffer is in memory. Use withClient, flush, and close at lifecycle boundaries. Durability starts after server enqueue. Monitor client drop counts separately from the server pipeline.

Retry only uncertainty or a transient failureKeep the same event ID when retrying a network interruption or retryable 503. Correct rejected entries and submit them separately; split requests rejected with 413. Equal retries of accepted entries are safe, while changed content requires a new event ID. Honor 429 Retry-After.

05

Resolve people from evidence

Level 3 · Identity policy & analytical consequences

Identity is an account-scoped query-time interpretation of observations. Raw events retain their original IDs. Binding evidence remains inspectable even when a device or cookie has been associated with several users.

Bindings respect shared devices

identify, identify_once, and alias create implicit cookie evidence. Mapped identifiers bind on any event with an explicit user. A nonempty same-cookie session can resolve pre-login activity only when it identifies one user; multi-user sessions remain ambiguous. Without session evidence, cookie uniqueness is evaluated across retained history.

Allowed mapped kinds are cookie, device, fingerprint, legacy email_sha256, and preferred email_hmac. Keyed email digests belong in a trusted backend; no pepper belongs in a browser.

Bound the resolution work

HTTP queries select account/date-scoped candidate contexts and prepare exact snapshots on their physical query connection. Compact signal, session, and context indexes avoid expanding raw JSON for every event.

Resident caps are 64 MiB for signal observations, 64 MiB for session observations, and 128 MiB for contexts. Index changes and fingerprint expiry invalidate caches; overflow fails the complete request rather than truncating identity.

Current person properties are a separate projection

identify v2 sets declared traits; identify_once v1 initializes them. The catalog currently declares string plan, signup_source, initial_plan, country, and role, plus numeric nonnegative-integer company_size. Legacy identify v1 remains identity-only. Server-owned first-acceptance eligibility prevents an old payload becoming a trait write after upgrade.

For each account/user/trait, the latest set wins; otherwise the earliest set-once wins, using occurrence time, receipt time, and event ID as deterministic order. Omitted keys leave state unchanged; null deletion is rejected. user:<name> dimensions use the resolved user's current value, so historical segmentation can change. Session traits belong to the first resolved user of the complete session. Anonymous subjects never inherit traits through matching raw text.

Retention and erasure cover replayable sourcesFingerprint evidence expires after 180 days; confirmed kansoku-admin apply-retention also scrubs expired fingerprint keys from raw and replayable inputs. User erasure removes current traits, scrubs discovered identity links, and optionally deletes explicit facts under a resumable fence. Minimal event dispositions prevent stale writer batches or archive replay from restoring erased state.

Typed filters and two dimensions

Standard routes accept one or two comma-separated groupBy dimensions and up to eight AND-combined filter groups, each with at most eight OR terms. Typed JSON terms, nonnested JSON {or:[...]} groups, and full shorthand terms separated by | share validation. Built-ins cover source/service, host/route, enrichment, acquisition and organization; declared prop:, current user:/org:, and cohort:<uuid> dimensions add segmentation.

Operators are eq, neq, in, contains, gt, lt, set, and unset. Operands use native parameters. Missing/null is distinct from empty string; comparisons, including neq, are false for unset values. Group keys retain their namespace. Support varies by route and population.

Whole sessions and closed days

Sessions assemble all retained web events before date/attribute filtering and are assigned to their earliest event bucket. Entry/exit use page-view routes. Bounce means one page view and no engagement; page_leave can extend duration without changing bounce.

Users, stickiness, lifecycle, and retention require a closed UTC observation window. Lifetime means retained history, so retention and erasure can change first observed activity. Normal hour/day/week/month grains remain route-specific.

Deterministic funnel chains and exposure diagnostics

Timelines order by occurrence milliseconds then event ID; one event cannot satisfy two repeated steps. Sequential mode skips intervening events, while strict mode requires adjacency across the full eligible timeline. For ordered unique counting, each start is considered; select greatest reach, earliest completion, earliest start, then event IDs. Exclusions stop further reach. Timing reports exact nearest-rank p50/p90 for the selected chains. Strict event filters are rejected because they could hide interruptions; participant selectors preserve complete timelines. Any-order mode opens a window at the earliest matching step and tracks distinct requested positions. counting=totals counts nonoverlapping attempts, restarting after completion, expiry, or interruption. Property attribution can use first touch, last touch, or step:<n>, including on experiment funnels.

Experiment diagnostics distinguish users exposed to multiple variants from mutually exclusive first-observed assignments and their shares. First observation is not an authoritative randomization log. Exposure counts, conversion denominators, and assignment shares answer different questions; the service does not calculate significance or select winners.

Saved cohorts and reusable definitions

Service-token CRUD at /cohorts stores behavioural or static definitions in PostgreSQL. Behavioural membership ANDs up to four frequency conditions plus optional current traits, over 1–365-day lookbacks anchored on the request's exclusive to. Membership targets identified users, including resolved pre-login activity. It is computed at query time, so identity, traits and definition edits can change historical segmentation.

Static uploads replace up to 50,000 explicit user IDs in one versioned ClickHouse insert under a cross-process PostgreSQL advisory lock. /cohorts/{id}/members and /size expose membership; definition/member lists use bidirectional cursors with default 20 and maximum 100 items. Filter with cohort:eq:<uuid> or split with groupBy=cohort:<uuid> into in/out groups. Static lists survive event retention; fenced user erasure removes their member facts.

/metric-definitions provides account-scoped CRUD and cursor lists for saved definitions. /metrics/custom evaluates an ad-hoc definition or a saved name through the shared compiler. Saved filters combine with request filters; request grouping/grain override simple defaults. Ratios aggregate numerator and denominator independently, are unbucketed, and reject event-property grouping. Definitions contain validated metric data, never SQL.

Organization populations and current attribution

Users, funnels, retention, signup conversion and feature adoption accept aggregate=organizations; user aggregation remains the default. Organization timelines merge actions across members, so different people can start and complete a funnel or retain the same organization. Person cohort selectors choose members before organization aggregation. Empty organization IDs are excluded; experiments, sessions, acquisition and paths retain their existing populations.

group v2 writes optional string plan, industry and country, plus nonnegative integral seats, into current org: traits. Group events with explicit user and organization IDs establish current membership. Latest state wins by occurrence time, first receipt time, then event ID. Default attribution uses the event's organization; attribution=user_organization on organization aggregation fills only missing organization IDs from a resolved user's current membership. Explicit event organization IDs win and anonymous subjects never inherit membership from matching text. Whole-session/acquisition sources reject organization dimensions.

Trusted SQL consumers

The constrained kansoku_reader role grants SELECT on only events_resolved, events_resolved_v3 and parameterized events_analytics_v1, with fixed read-only, time, memory and result limits. Published user, revenue and two-step funnel recipes reproduce their stated HTTP populations; Grafana and GrowthBook have real consumer acceptance. SQL access is a trusted single-tenant operator surface spanning all accounts. It does not acquire the HTTP maintenance fence: pause external schedules during maintenance and manage downstream copies separately.

Bounded complete answersQueries accept positive UTC half-open ranges of at most 366 days, 1–20 funnel steps, a maximum 90-day funnel window, paths of 1–10 transitions with top 1–20 per step and up to a 90-day window, and up to 32 retention offsets in 1–365. Answers contain at most 10,000 points. Default budgets are 30 seconds including pool wait/preparation and 512 MiB native memory. Oversized results or resource exhaustion return a complete 400 error without partial data.
SQL safety and errors

Allowlisted dimensions, registry-checked scalar types, native operand parameters, and authenticated account scope constrain SQL. Unknown or duplicate scalar query parameters fail explicitly. Validation and resource-limit problems are permanent 400s; other storage failures remain retryable 503s. All use RFC 9457 application/problem+json.

Valid empty queries normally return an empty points array; documented ungrouped series and zero-denominator ratios emit zeros. Resource lists use cursor pagination; metric aggregates remain complete-or-error answers. Pagination errors use the documented Relay JSON shape.

07

Observe the pipeline, recover deliberately

Level 3 · Deployment, failure modes & tuning

The operational unit includes two durable databases, an HTTP service, and asynchronous work. A live listener alone says little about how quickly accepted events become queryable.

Deployment order

Migrate before serving

  1. just migrate: install the vendored PGMQ schema and application credential, acceptance, quarantine, maintenance, cohort, metric-definition, and native-administration session tables through PostgreSQL's migration ledger.
  2. kansoku-ch-migrate: execute the compiled native plan under a persistent PostgreSQL maintenance session with retained target/server/ledger identities and external drain evidence. Follow the initialization and upgrade runbook; native history lives in the separate kansoku_migration_ledger database.
  3. Issue account credentials with kansoku-admin issue-key or just issue-key, then start kansoku-server.

Normal startup provisions the queue; it performs neither schema migration. PostgreSQL does not require an upstream PGMQ extension installation for this vendored schema path.

Runtime evidence

Liveness, readiness, traces

Use /health/live and /health/ready for orchestration. Readiness checks writer life, PGMQ, native ClickHouse query reachability, queue depth, and stale flushes. External checks have 750 ms deadlines; the complete probe has a two-second deadline.

/internal/metrics exports Prometheus instruments. Non-probe requests emit correlated JSON access records and bounded route spans without query values, bodies, cookies, or credentials. OpenTelemetry export is opt-in; providers flush on shutdown.

Accepted counters include equal retries; newly queued counters do not. Writer counters reflect physical deliveries, so these are not an equality invariant. Watch backlog age, archive growth, breaker state, and recovery failures together.

Administration is fenced and resumable

kansoku-admin issues/lists/revokes keys, previews and confirms user erasure, applies retention, replays/purges archives, and inspects/purges rejections. Confirmed lifecycle jobs persist a global fence, wait for admitted traffic and native inserts, journal idempotent stages, then rebuild current projections, including organization traits and membership, and verify before releasing traffic. User erasure also removes static cohort membership. Failed jobs keep the fence and resume by job ID. This coordinates stores without claiming a cross-database transaction.

Retention advances an explicit snapshot cutoff; setting KANSOKU_EVENTS_RETENTION_DAYS alone changes nothing. Zero/unset means unlimited future retention. Confirmed application expires raw and replayable payloads, rebuilds derived state, and separately scrubs expired fingerprint keys. Canonical queries enforce the applied cutoff immediately; physical TTL is cleanup. Schedule the command to advance the cutoff periodically.

Archive replay uses row locks and a unique physical-queue/archive-ID ledger in the same PostgreSQL transaction as resend. Repeated commands cannot resend a completed archive row. Acceptance hashes, replay identities, and erasure dispositions remain indefinitely so old deliveries cannot resurrect deleted facts or traits.

Deployment owns the perimeter and schedulingTerminate TLS and configure network policy externally. Restrict unauthenticated operational routes at the proxy/network boundary. CORS covers /v1/*; beacon origins are enforced before side effects. Operators own backups, finite disk/WAL capacity, maintenance scheduling, and restoration policy that preserves cutoffs and erasure ledgers.

What the architecture promises today

Level 1 · Shipped scope & deliberate constraints
Implemented in this checkout

Replay-safe analytics with reusable populations

Single, partial-batch and beacon ingest; immutable acceptance; bounded recovery; conservative identity; enrichment/acquisition and sessions; exact activity/retention; extended funnels and paths; saved behavioural/static cohorts; custom definitions and OR filters; person/organization traits and organization aggregation; typed Haskell clients; fenced administration and telemetry.

Product boundary

External consumers, explicit operating limits

Versioned SQL projections and a constrained reader support verified Grafana/GrowthBook consumption. Kansoku provides no built-in dashboard UI, significance engine, key-management HTTP API, automated backups, or hosted service. Optional Swagger UI/Redoc remains deferred.

Browser SDK implementation lives in mori://shinzui/kansoku-ts; EP-38 records completed cross-project release acceptance, including browser beacon, identity and trait conformance. A common account does not itself establish cross-origin identity; SDK storage/handoff must establish that link.

The architecture favors batched analytical throughput and explicit semantic contracts. Freshness is asynchronous; current identity, traits, cohort definitions and organization membership can reclassify retained history. Exact HTTP populations remain distinct from explicitly approximate raw-identity exposure sketches. Maintenance pauses protected HTTP traffic globally; trusted SQL consumers coordinate their own pause.
