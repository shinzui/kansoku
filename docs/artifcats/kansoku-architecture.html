Kansoku is a first-party, self-hosted analytics service. It turns browser and backend events into account-scoped metrics through a durable PostgreSQL queue, a supervised batch writer, and ClickHouse.

01

The system in one picture

Level 1 · System context

Producers submit facts. Kansoku validates and buffers those facts durably, writes them efficiently, and exposes named analytical questions. Applications retain ownership of their business workflows and user records.

Write boundary

202 means queued

HTTP acceptance follows durable enqueue. Query visibility follows a later ClickHouse flush; acceptance provides no read-after-write guarantee.

Read boundary

Metrics have semantics

Queries choose raw facts, current identity resolution, or precomputed aggregate states. Exact and approximate results answer different questions.

Ownership boundary

Facts stay analytical

Kansoku owns analytics contracts, credentials, identity evidence, and metrics. It does not run application business workflows or own account records.

02

One service, coordinated lifetimes

Level 2 · Runtime components

Warp, the writer, and the queue-depth poller share one process. Unexpected writer or poller termination brings down the HTTP lifetime, allowing the deployment supervisor to restart a coherent service.

Startup sequence
  1. Load configurationParse environment settings and install SIGTERM / SIGINT handlers.
  2. Acquire durable connectionsCreate the PostgreSQL pool; provision the named PGMQ queue after migrations have installed its schema.
  3. Prepare reads and telemetryCreate the ClickHouse query pool, trace provider, pipeline instruments, heartbeat, and queue sample state.
  4. Start coordinated workRun the writer and poller asynchronously; race their lifetimes against the HTTP server.
Concurrency & resource ownership

Keep inserts off query sockets

The writer owns a dedicated, cached ClickHouse native-protocol connection. A failed insert discards that handle; the next delivery opens a fresh one.

Metric handlers borrow from a separate fixed-size pool, defaulting to four query connections. PostgreSQL pooling is shared by credential checks, queue producers, and queue processing.

Effects stay explicit

The base runtime uses Log, Reader Config, and IOE. Ingestion and writer runners add queue, error, concurrency, and tracing interpreters where needed.

The writer's acknowledgement boundary

A Shibuya batch processor groups messages under one batch key, without aggregate ordering. Decoding happens per message, followed by one ClickHouse insert for all valid events. This is a throughput-oriented ingestion pipeline.

Decisions made by writerBatchHandler
OutcomeValid queued messagesMalformed queued messages
Insert succeedsAcknowledge after the insert; update written-event counter and heartbeat.Dead-letter independently.
Insert throwsRetry with a five-second delay. An uncertain insert can be delivered again.Keep dead-letter decisions; include failure context.

Finite retry policy, durable archiveThe adapter's default dead-letter behavior archives messages. Retry-budget exhaustion can move otherwise valid events to the archive during a long outage. Recovery can require operator inspection and replay; it is not an unlimited automatic retry guarantee.

The writer configures StopAllOnFailure. Its shutdown path requests a graceful drain with a 30-second timeout when it observes the shutdown signal. The outer process also coordinates cancellation, so deployment termination must allow a grace period and queue redelivery remains the recovery boundary.

03

Follow an event across the durable boundary

Level 2 → 3 · HTTP contract & processing sequence

Both ingest routes authenticate the producer, replace the claimed account with the credential's account, stamp the server receive time, and validate the canonical event before queueing.

Authentication

Account identity is authoritative

ksk_w_… write keys permit ingestion. ksk_s_… service tokens permit ingestion and metric reads. Both are accepted through Bearer authorization or X-Api-Key.

Authorization takes precedence if both headers exist, even if malformed. Each request checks a SHA-256 token hash in PostgreSQL; revocation takes effect on the next request.

HTTP admission

Reject at the right level

Defaults are 5 MiB per body and 500 events per batch. Invalid JSON or an array that cannot decode returns 400. Body or batch overflow returns 413.

A decoded, in-limit batch partitions events independently: valid entries queue, invalid entries return zero-based rejection indices. Successful batch processing returns 202 even if every event is rejected.

Schema governance is executable

The registry in kansoku-api drives validation and the deterministic schema catalog. An omitted schemaVersion means version 1. A declared event must match an existing version and its property contract; undeclared names remain accepted without property-schema checks. Supplied versions must be in 1..65535.

GET /v1/schemas publishes the catalog; GET /openapi.json publishes route and wire types. Committed JSON mirrors are generated with just contracts and just openapi. Released event versions are maintained through explicit governance.

Producer SDK boundary and delivery behavior

The Haskell client derives routes and types from kansoku-api. Defaults: batches of 100, a five-second flush interval, a 10,000-event memory buffer, five retries, and 100 ms exponential-backoff base. Buffer-full drops, permanent delivery failures, and server-side rejections increase droppedCount.

The SDK buffer is in memory. Use withClient, flush, and close at lifecycle boundaries. Durability starts after server enqueue. Monitor client drop counts separately from the server pipeline.

Retry only uncertainty or a transient failureKeep the same event ID when retrying a network interruption or retryable 503. Do not resend an entire successfully processed partial batch. Correct rejected entries and submit them separately; split requests rejected with 413.

05

Resolve people from evidence

Level 3 · Identity policy & analytical consequences

Identity is an account-scoped query-time interpretation of observations. Raw events retain their original IDs. Binding evidence remains inspectable even when a device or cookie has been associated with several users.

How evidence is created

On identify and alias, anonymousId creates an implicit cookie binding to the explicit user. Entries in identifiers bind on any event that carries userId.

Allowed keys are cookie, device, fingerprint, and email_sha256. Values must be 1–256 printable, non-space ASCII characters. The explicit identifier map need not repeat the implicit cookie.

What “exact” does and does not mean

Exact user metrics compute distinct canonical users under the current evidence and policy. That makes the count exact for the chosen identity model; weak signals and shared devices can still misidentify a person.

identity_conflicts retains visibility into signals associated with multiple users. Equal-confidence bindings prefer the newest observation; a complete confidence-and-time tie has no additional documented winner.

Evidence retention and raw retention are separateThe 180-day TTL removes fingerprint evidence. Raw events still retain their identifier map unless an operator runs the documented scrubbing mutation. Per-user erasure must address both raw identifiers and evidence; these maintenance procedures are not automated by the server.

A semantic layer over several read paths

Level 2 → 3 · Query compilation, accuracy & API surface

Metrics are named definitions and specialized analytical queries. The API validates dates, grains, dimensions, and endpoint-specific parameters, injects account scope from the service token, compiles SQL, and decodes typed results.

Time and grouping

Dates use UTC half-open intervals: from ≤ time < to. Standard grains are hour, day, week, and month; supported grains vary by endpoint.

Standard metrics accept exactly one dimension: event_name, source, route, or prop:<name>. Property grouping requires fixed registered event names that all declare the property. Ratio metrics reject property grouping.

Analytical windows

Funnels require a non-empty ordered step list. The window is 1–7,776,000 seconds (90 days); the default is the requested range duration capped at 90 days.

Retention defaults to offsets 1, 7, 14, and 30; offset 0 supplies cohort size. Experiment exposure is emitted when the variant is viewed, not merely assigned. Registered experiment/variant values use [a-z0-9_.:-]{1,128}.

Do not mix raw-identity and stitched denominatorsA person seen anonymously and later logged in may contribute two raw identities to exposure or active-user rollups, while exact conversion or funnel queries resolve one canonical user. Approximate sketches have about 0.8% relative error at scale; identity-model differences are a separate source of disagreement.
SQL safety and response behavior

The query layer uses validated dates, allowlisted dimensions, registry-checked property names/types, and SQL literal handling rather than accepting arbitrary client SQL. Account scope comes from the authenticated principal. Validation rejects unsupported combinations before database execution.

A valid query with no matches returns 200 with an empty points array. Database execution failures return a retryable 503 instead of invented zero-valued data. Common error envelopes carry code, message, and retryable. Contract placeholders for acquisition, organizations, and custom metrics return 404 not_implemented.

07

Observe the pipeline, recover deliberately

Level 3 · Deployment, failure modes & tuning

The operational unit includes two durable databases, an HTTP service, and asynchronous work. A live listener alone says little about how quickly accepted events become queryable.

Deployment order

Migrate before serving

  1. just migrate: install the vendored PGMQ schema and API-key table through PostgreSQL's migration ledger.
  2. just ch-migrate: apply ordered ClickHouse SQL and record analytics.schema_migrations.
  3. Issue account credentials with just issue-key, then start kansoku-server.

Normal startup provisions the queue; it performs neither schema migration. PostgreSQL does not require an upstream PGMQ extension installation for this vendored schema path.

Runtime evidence

Liveness, readiness, traces

/health checks only HTTP liveness. /ready checks writer life, PGMQ reachability, queue depth, and stale successful flushes while backlog exists. Failure returns 503.

/internal/metrics exports Prometheus instruments when enabled. OpenTelemetry trace export is opt-in through the configured exporter environment; the default tracer makes no exporter connection.

Deployment owns the perimeter and durable-data lifecycleWarp does not terminate TLS. Configure TLS and network policy externally. Backups, topology, raw-event retention, archive replay, and identity scrubbing remain operational responsibilities.

09

What the architecture promises today

Level 1 · Shipped scope & deliberate constraints
Implemented

A usable analytics backend

Authenticated single and partial-batch ingestion; versioned schema publication; durable queueing; supervised ClickHouse batching; multi-signal identity evidence; typed properties; product, funnel, retention, revenue, and experiment analytics; Haskell producer and metrics clients; readiness and telemetry.

Not shipped

Bounded product surface

Browser/React SDKs, a dashboard UI, and hosted/container distributions remain future work. Acquisition, organizations, and custom metric routes are reserved contract placeholders. Key-management HTTP endpoints, a revocation CLI, automated backups, and automatic identity-retention maintenance are absent.

The architecture favors batched analytical throughput and explicit semantic contracts. It accepts asynchronous freshness, duplicate-tolerant query design, and an operational archive-replay boundary. Query-time identity keeps historical interpretation flexible; join-free rollups trade that flexibility for speed.
